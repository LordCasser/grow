# 1.1.2 — 2026-08-03

## Behavior Changes

- **斜杠输入不再是模型提示词。** 任何以 `/` 开头的输入都会先由 Grow 解析；未知命令直接报错，
  不再降级进入模型 prompt queue。
- **Goal 中的 Send now 使用 interjection。** 它会在当前 turn 的下一个安全边界注入，而不是等待
  goal 完成或通过普通 send-now 路径取消 turn；队列移除和注入缓冲写入是同一个原子状态变更，
  不会重复执行。
- **Goal Behavior 生命周期与 Goal lifecycle 分离。** pause、budget 限制、目标修订和自动 back-off
  都保持 Goal Behavior；只有 `/goal clear` 或 verifier 确认完成后自动回到 Normal。通过 Behavior
  picker 进入 Goal 后，首条普通文本等价于 `/goal set`。
- **图片与 PDF 阅读采用显式模型路由。** 未配置 `[models].image_description` 时，`read_file`
  返回的图片和 PDF 页面保持为主模型可见的多模态工具结果；显式配置后只由该辅助模型解释，失败
  会作为文字错误返回，不会静默切换模型。

## Fixes

- Goal 执行期间可以继续提交普通消息；Enter 进入 shell 权威 FIFO 队列，与其他 Behavior 的
  输入语义一致。
- 新增 `grow/commands/execute` 控制面。Goal 命令在 idle 和活跃 turn 中都不会作为用户消息进入
  模型上下文，而是输出与 `/model` 一致的响应日志。
- `/goal budget` 只修改资源约束；`/goal resume` 只修改生命周期；`/goal set` 原位修订目标并
  保持当前执行。三者都不取消 turn，只有显式 `/goal pause` 会中断当前 Goal。
- 活跃 Goal 的 `/goal clear` 会被拒绝，必须先 pause；暂停前尚未消费的 interjection 会恢复成
  排队消息，避免用户补充说明丢失。
- `/goal set` 的 Tab 补全会提供当前 Goal 内容，所有非清除状态都可直接编辑。
- 修复 Goal setup 在 actor command handler 内等待 planner 导致的自锁：Behavior 状态与
  `CurrentModeUpdate` 在控制面立即提交，planner/implementer 工作由隐藏 `GoalControl` turn 承担，
  Goal 不会再停在 `Planning` 而不执行。
- planning 中收到 `/goal set` 时会丢弃旧 revision 的 planner 结果并对最新目标重新规划；pause
  同时清理瞬态 Planning/Verifying 标记，避免取消后残留假运行状态。
- Goal 控制 turn 是不可被用户优先级清扫的持久队列项；普通 completion wake 仍可被新用户消息
  替代。暂停、TUI 取消或确认切离 Goal 时尚未消费的 interjection 会恢复为排队消息而不会丢失。
- 修正隐藏诊断命令带参数时的行为：现在返回用法错误，不会把原始斜杠文本发送给模型。

## Architecture

- Pager 只负责输入分类与传输选择；session actor 统一拥有 prompt FIFO、interjection fallback、
  slash command 执行、Goal 状态和 turn 取消。
- 命令控制面与 prompt admission 共用 actor mailbox，因此只承担有界状态转换。任何会把事件送回
  同一 mailbox 的 planner、sampler 或 subagent 工作都必须转为独立 turn；详细不变量见
  `docs/architecture/input-routing.md`。
- Goal 定义使用单调 revision；planner、evaluator、verifier、strategist 和 summarizer 只能提交
  与当前 revision 匹配的异步结果。
- 图片描述配置以 `Option<String>` 穿过配置、子 Agent 和 session 边界；typed `ReadFileOutput`
  在 tool-result chokepoint 决定多模态或辅助描述路径。详细不变量见
  `crates/codegen/shell/docs/architecture/image-reading.md`。

## Distribution

- 官方 workflow 构建并验证 10 个 Release 资产：macOS、GNU/musl Linux、Windows 的主要
  x86_64/arm64 目标、Linux riscv64，以及 OHOS arm64。
- OHOS 构建固定到已验证的 HarmonyBrew 镜像 digest，并按实际 toolchain 布局判断 Rust 是否已
  安装，避免 `brew --prefix` 对未安装 formula 返回预期路径导致发布失败。
- OHOS 产物校验跟随实际 Cargo profile 目录，`release-dist` 不再被误判为缺少二进制。
