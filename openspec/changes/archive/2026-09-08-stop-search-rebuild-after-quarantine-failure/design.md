# Design
Use an io::Result around the existing optional main quarantine path. Attempt rename directly; a source NotFound can be treated as absent, while other errors stop the attempt. Do not silently leave a failed sidecar in the live namespace and proceed to create a replacement database. Keep paths already moved in quarantine if a later operation fails; do not roll them back over potentially newer live files. This is fail-stop recovery, not an atomic multi-file filesystem transaction.

Inspect cache-epoch consumers before implementation. Any partial namespace change must be observable to existing in-process invalidation, but an epoch change must not be described as proof that recreation succeeded. Recreate failures and missing-main successes need distinct outcome logging. Do not introduce another persistent store or silently delete quarantine artifacts.

A deterministic temporary-path failure can use a valid near-limit basename whose appended quarantine suffix exceeds component limits. Verify failure prevents recreate and preserves the source files. Also test successful isolation, absent files and failed recreate. No root-permission assumptions, user-cache mutation, arbitrary retry or full cross-process SQLite concurrency redesign.

Caller audit: both search_fts::with_index and open_or_create currently reopen unconditionally after heal_unusable. Return a boolean retry permission from healing: healthy-under-reprobe or successful recreation permits reopening; lock/probe/isolation/recreate failure denies it and the caller returns its original triggering error. Detailed failure stays in healing diagnostics. Invalidate CACHE_EPOCH after any successful quarantine rename, including a later partial failure; a subsequent successful recreation also invalidates. The counter is a change token, not a count of completed repairs.
