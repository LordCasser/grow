# Design

The worker already serializes process-local appends, and `LogWriter::append_lines` takes the shared inode lock across processes. Move the final capacity decision into this critical section. Open the persistent writer read/write, without `O_APPEND`; append explicitly seeks to EOF under the lock. If the opened descriptor's length plus the complete byte slice would exceed `MAX_SIZE`, verify that the path still names the locked inode and run the existing bounded-tail trim algorithm on that same descriptor. This avoids opening a second handle under a mandatory Windows file lock. Read its length again before appending. A mismatch, I/O error, untrimmable tail, or still-insufficient space rejects the append.

Extract the read/rewrite/truncate portion of `trim_file` into a helper that accepts an already-open read/write handle. The public maintenance trim retains its current nonblocking lock policy. The append path holds the writer lock while calling the helper; this avoids lock reentry and keeps the historical tail selection. A queued loss diagnostic and its subsequent record form one append slice and are admitted or rejected together.

The limit applies to completed Grow appends of a valid JSONL log. It does not undo bytes written by unrelated processes that disregard the advisory lock, nor can it repair a pre-existing file with no complete newline in the bounded trim window. In that case it refuses to grow the file. The regression writes enough complete records inside one maintenance interval to cross the old threshold and checks each completed append's file size and record boundaries. A second test uses independent writer handles to exercise the shared inode lock.
