# 实际用户旅程的对抗性分析

> 本文保留该阶段的证据与缺口。最后联合测试和收口状态以 [release-verification.md](release-verification.md)、[joint-task-evidence.md](joint-task-evidence.md) 为准。

范围仅为本 change 的消息投递、流程控制和上下文消费。按入口、执行阶段、结果、控制交错和恢复方式划分可达等价类；不把所有角色/布局的笛卡尔积重复列成测试，也不声称穷尽任意调度。具体源码入口和已有测试见 [源证据矩阵](user-journey-matrix.md)。

证据等级区分：模型=demo 中的转移/反例；运行=本次真实 Rust 测试；源码=已核对实现但没有独立集成旅程；边界=选定语义有意允许的效果。后续运行结果以 verification 和实现记录为准。

## 1. 必须成立的完整旅程

| ID | 用户实际操作与交错 | 应有结果 / 问题判断 |
| --- | --- | --- |
| J01 | child 在工作中问 parent | child 得原工具结果；parent 的独立 Sideband 回答后产生自己的被动事实，不把 child 变成人类或上行控制者。 |
| J02 | parent 正等待 child，child 反问 parent | 咨询不依赖 parent 前台退出等待，不能把新问题排成 parent 的普通用户任务造成互等；原等待只由原 child/tool 结果结算。源码与既有路由覆盖，精确交错尚缺独立集成测试。 |
| J03 | parent 询问正在工作的 child | child 主任务继续；回答只作为咨询，修改任务仍用已有显式消息。 |
| J04 | 主会话询问另一个 Session | 仅真实目标同步；来源保留原工具结果，不获得第二条合成输入。 |
| J05 | 外部 API 发起询问 | 返回 API 调用者；不冒充来源 Session 的模型工具调用。目标成功事实仍可被动消费。 |
| J06 | parent/peer 的 cwd 不同 | peer 继续按既有批准路径，delegation 继续依既有 runtime 关系；回写不扩大授权范围。 |
| J07 | 问无关/已终止/隐藏 Workflow child | 原路由拒绝，没有成功证明或上下文通知。 |
| J08 | 回答方 idle，只有咨询完成 | UI 可显示 Answered，但不新开模型 Turn；下一次真实任务才消费。已运行直接无唤醒回归。 |
| J09 | 回答方正在推理/流式输出 | 当前请求不取消、不改写；后继获准请求看到问答。真实 Sampler 非抢占用例已通过；完整真实 inquiry→Sampler 的联合用例正在补充。 |
| J10 | 回答方正在执行工具批次 | 不取消工具或拆开 call/result；下一安全边界消费。模型与源码已核对，单独工具阻塞的联合咨询旅程未运行。 |
| J11 | 回答方正在依赖/权限等待 | 咨询不代替原等待的完成、批准或取消；待下一实际采样再纳入。专门重叠旅程尚缺集成覆盖。 |
| J12 | 问答在最终候选快照前完成 | 精确候选能使仍获准的同一 Turn 续一个 Step；不能先消费再越过预算或取消。 |
| J13 | m1 促成合法后继，m2 在旧快照后到达 | m2 不能改变旧候选决定，但可进入新安全边界；无需给它另造 minimum-Turn 路由。模型已重放；固定 ID 消费运行回归覆盖接缝。 |
| J14 | 最终关闭已胜出后回答才完成 | 保留待消费信息，不复活已结束 Turn，不单独唤醒。已运行对应边界回归。 |
| J15 | Goal 活跃且仍有预算 | 按原 Goal 准入消费；注入不创建新的 Goal 定义或预算。 |
| J16 | Goal 暂停、阻塞或预算用尽 | 不因回写恢复 Goal；待原本获准的执行。暂停与预算不是同一个状态；精确跨暂停→恢复旅程尚缺独立联合测试。 |
| J17 | 读正文期间取消/Behavior 控制关闭旧 Turn | 消费 admission 重新验证精确 owner/资格，保持未消费；已经提交的消费则留在历史、禁止越权继续请求。已据审查修正。 |
| J18 | 用户 FIFO 队首正在编辑 hold | 被动信息不能绕过 held 用户输入打开通知 Turn；编辑保存/撤回仍由原 FIFO 仲裁。模型与源码覆盖，未专门重跑完整 UI 旅程。 |

## 2. 失败、重试与长内容

| ID | 用户遇到的情况 | 应有结果 / 已发现问题 |
| --- | --- | --- |
| J19 | 询问被拒绝、取消、超时、provider 失败或空回答 | 原 typed 终态，不能产生“成功问答”。不是把失败注入为一份成功答案。 |
| J20 | Sideband 成功，成功 audit 尚未提交即存储失败 | 不向调用者伪造已确认成功；保留实际 Sideband/usage 证据，沿原提交失败语义处理。 |
| J21 | 成功 audit 已落盘，Received 尚未落盘 | 成功事实是同步义务。live/冷恢复协调后才让依赖该边界的请求发出；不能只看 Received 集为空便跳过。模型反例促成了这一修正。 |
| J22 | Received 已提交，ACK 丢失，原操作重试 | 使用原 identity 核对真实提交；不重跑 Sideband、不生成第二份收据。 |
| J23 | 必需正文丢失/不可读 | 真实请求失败且保留未消费事实，不能当空 inbox 继续。真实 handle_prompt 零 provider 请求回归已通过。 |
| J24 | 首次/后继/最终候选的 Consumed 提交失败 | 不发依赖该输入的请求。已运行严格三分支故障用例，不能让 completion recovery 自动再采样。 |
| J25 | Consumed 提交后、发请求前崩溃 | 恢复已有 Surface，不再消费一次，不声称模型曾读过。模型与持久事实规则覆盖。 |
| J26 | 底层写失败导致清理也失败 | **发现并修正：** input_terminal 清理曾覆盖原 notification-consumption 错误；现保留原始 cause，用户能定位最初故障，同时仍如实报告终态未持久化。 |
| J27 | 回答很长，原文合法但完整问答超过通知上限 | **发现 P1：** Sideband/JSONL 可达 64 MiB，通知限 1 MiB；先提交 Answered 会形成永久不可同步义务。修正为按完整 renderer 的 UTF-8 字节数复用既有上限，在发布成功终态前决定可否接纳。超限返回明确失败，保留 Sideband 证据，不截断/重试。新增真实 provider 边界回归待汇总。 |
| J28 | 同 inquiry ID、同 payload 重试 | 复用原结果和收据；新版本字段不能使同一逻辑询问再注入一次。 |
| J29 | 同 ID 更换目标/问题/正文 | 拒绝冲突，不覆盖旧事实，不按文本相似度生成新身份。 |
| J30 | 不同 ID 的问题或答案恰好相同 | 两份真实询问分别处理；不能按正文去重。模型覆盖；完整前台展示的专门联合测试尚缺。 |
| J31 | 多人同时问同一回答方，或超过现有排队容量 | 使用原 inquiry FIFO/Busy 规则；每条成功有独立来源，不中断 foreground。队列容量不因 inject 改变；批量并发到前台消费的联合压力旅程尚缺。 |

## 3. 导航、恢复与所有权

| ID | 用户操作 | 应有结果 / 问题判断 |
| --- | --- | --- |
| J32 | 看到 Answered 后打开另一个页签或 Dashboard 预览 | 导航不消费上下文，不说明回答方模型已读；消费者是实际 Session 的获准采样，非页面焦点。 |
| J33 | Normal/Minimal 切换、断线、重连或 UI replay | 只重建同一通信行；不得重新询问、重复注入或把显示恢复当运行时修复。既有显示契约与当前源码覆盖；本次未新增 UI 自动化。 |
| J34 | 用户 Stop 当前 Turn，Sideband 稍后完成 | 不靠 inject 重新启动已停止 Turn。Sideband/Turn 的取消范围按原 owner 区分；仅停止 Turn 不等于整个 Session 已退役。 |
| J35 | 用户关闭或挂起后再恢复 | 新接纳关闭；canonical 未消费义务留原 Session。挂起树恢复 gate 未打开前不得派生 Received，开放后的首边界再协调。已发现并修正 startup/live gate 遗漏。 |
| J36 | 回答方崩溃，询问只有 open receipt | 收束为 TargetRestarted，不偷偷重新问一次；没有成功证明就不注入成功问答。 |
| J37 | 回答方崩溃，已有成功证明但没有收据 | 原合法 writer 重建收据；只读列表/trajectory/replay 不获取写权修复。 |
| J38 | 从包含问答的历史 fork | 可继承历史文本，不继承原 pending 消费权、权限或树恢复资格。对应证明的 owner 不等于 fork，不能重建本地待办。 |
| J39 | rewind 或压缩后继续 | 这些操作仍由原机制管理。消息路径遵守其当前合法 Surface/owner，不撤销过去消费、重新授权或把摘要当精确回执。 |
| J40 | 删除存在问答的 Session | 先经过原 preflight、runtime drain 与 canonical 依赖检查；成功删除不是简单 UI 移除。其他会话已保存的原工具结果独立保留。删除与在途 inquiry 的精确竞态尚缺专门联合测试，不把它声明为无条件可删。 |
| J41 | 导入/读取孤立或篡改的证明/收据 | 拒绝无原证明、错误 source/owner/version/正文指纹、重复成功、错问题/结果和前向 Spawn；不是自动“修好”错误身份。已补真实 ledger 校验回归，最终结果见实现验证。 |
| J42 | 咨询收据被标记 Consumed 但 input=None | 拒绝，不能清除待办却未发布模型输入；其他 producer 的合法 None 规则保留。ChatState 全量包含本回归已通过。 |

## 4. 混合操作与多端体验

| ID | 用户操作 | 应有结果 / 证据边界 |
| --- | --- | --- |
| J43 | parent/child 或两个 peer 同时互问 | 不把咨询变成对方 foreground 用户任务；各自独立 Sideband/receipt，不生成自动 ACK/询问循环。现有工具无工具咨询及队列规则支持该解释，双向重叠的完整联合测试未运行。 |
| J44 | ask 的旧快照回答与新的 send/steer 指令同时到达 | 真实 send/steer 保留原执行控制效果，不能把其抢占归因于 inject。咨询是冻结快照意见，不能声明覆盖后来的显式指令。已有消息与普通通知分组消费不承诺跨类型全局正文顺序，未进行模型语义取舍评测。 |
| J45 | 询问过程中切换模型、Agent 或 Behavior | 原 Sideband 仍属于自己的冻结来源/route；问答不取消或实施配置变更。后续消费服从当前合法 owner 与边界，不让旧咨询激活已退役协议。精确重叠的咨询联合测试未运行。 |
| J46 | 用户允许跨目录询问，然后断开 UI | “允许询问”不扩大写权限；已完成批准后按原 inquiry 生命周期处理，批准前失去必要 UI 按原拒绝/不可用规则返回。问答不生成 PermissionEvidence；不是“点允许后自动让主任务执行”。 |
| J47 | 同一 Session 多端查看，Dashboard/详情/Minimal 来回切换 | 这些视图只展示同一事实，不能各自触发一次消费。接收方的上下文属于 Session runtime，不属于选中行、页签或某个客户端。依据既有客户端契约；本次未重复全部终端自动化。 |
| J48 | 上下文变化后，用户又问同一句问题 | 新 inquiry identity 才代表新查询并使用新的冻结快照；原 identity 重试仍返回原结果。不能按正文相同复用旧回答，也不能把 get_inquiry 查询当重跑。 |
| J49 | 问答消费后长时间工作，历史被压缩 | 原 canonical 证据可追溯；当前模型请求可按已有压缩规则包含摘要，不能承诺原问答永远逐字占据当前窗口。压缩不由本消息路径控制。 |
| J50 | 用户频繁咨询或要求大段分析 | Sideband 与上下文都消耗 token，可能触发已有预算/上下文压力规则。超限单条问答的新边界已实际回归；任意多询问的吞吐/成本和极端聚合压力没有做完整性能试验，不宣称无限容量。 |

## 5. 仍必须明确的产品边界

- **当前响应可能过时。** inject 不改已经发出的请求。回答方仍可能在旧响应或旧工具批次里说出“我没回答过”；只能保证下一获准请求可见新问答，不能撤回已输出文本或已执行副作用。原截图中的问题会改善，但不能承诺在途误判绝不发生。
- **咨询不等于前台采纳。** 回写的是“本会话的独立 Sideband 实际回答了什么”，不是“前台主任务已作正式决定”。两者可以不一致；授权和正式任务变更仍走原控制/消息机制。单凭前台没有记忆不能证明回执伪造，判定应核对真实事实。
- **没有唤醒不等于没有费用。** ask 自己仍有一次 Sideband 调用，之后纳入上下文也有 token 成本；已有 Goal 预算可能因此关闭后继准入。这是预算控制，不是 inject 发出取消信号。
- **当前前台尚未消费的咨询，后一次 Sideband 不承诺已看到。** 它仍从自己的冻结 Surface 回答；不能为了“即时共享记忆”另建旁路上下文库。

这些是所选非抢占、被动同步语义的边界，不应偷偷改成 interrupt 来消除。最重要的覆盖缺口是把真实 inquiry/proof 生成与真实 foreground request 串成一次完整正向旅程，已派发补测；其余未运行的组合应保持可见，不能写成已经穷尽验证。

## 6. 实际补测后的更新

实现者已补齐并运行真实接收端 inquiry→InfoRequest→canonical proof→Received→真实 foreground 同 Turn 后继请求的联合用例，同时核对重试不产生额外 HTTP 请求/收据。它与现有工具/peer 路由身份回归共同覆盖接缝，不宣称已逐个运行四种前端入口的完整跨进程旅程。

最终新增的四个真实 message_delivery 用例已通过：阻塞采样非抢占、首次/后继/最终消费故障、真实 inquiry 联合正向链路、完整字节上限和失败后继续工作。ChatState 最终相关构建通过 610 项、3 项既有忽略；上限修正后的 Shell 最终全量通过 4492 项、9 项既有忽略。精确命令、源码指纹和依赖检查由实现验证记录汇总。

J27 的问题已在生产实现修正并通过真实 provider 边界回归：完整 UTF-8 正文恰好 1 MiB 可接纳，多一字节失败；raw answer 本身为 1 MiB 时也因元数据开销被正确拒绝，保留 Completed Sideband 且后续正常 foreground 可继续。冷加载也拒绝包含不可投递本地成功义务的 malformed proof。其余标为缺少独立联合测试的旅程没有因这次补测被自动升级为“已运行”。

另对 J35/J40 的疑似“已有结果重试与关闭并发，收据晚于挂起 checkpoint 落盘”进行了调用链核对：实际 RunCoordinationInquiry 通过 mailbox 投递，run_loop 内联等待 enqueue 完成；SuspendRuntimeNode 的 checkpoint 命令排在该重试之后。早先接纳的写入可在 SuspendRequested 后完成，但不能因此越过 node checkpoint；运行中的新回答另持有原 Queue activity，前台协调则随 foreground 收束。未发现该疑似死锁/晚写路径可达，因此没有为它新增锁、活动账本或保护 wrapper。
