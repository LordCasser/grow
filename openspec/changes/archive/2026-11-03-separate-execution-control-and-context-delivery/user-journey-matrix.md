# Consultation delivery: practical user journeys

> 初期只读盘点，保留当时的覆盖缺口以便追溯；后续联合测试、修正和最终证据以 [joint-task-evidence.md](joint-task-evidence.md)、[joint-verification.md](joint-verification.md) 与 [final-independent-review.md](final-independent-review.md) 为准。下文的未覆盖标记不表示最终仍未完成。

This matrix follows the current actor/runtime paths and the tests added with this change. It treats a successful answer as **available context**, not proof that the provider has seen it. “Tested” means a matching test exists in source; this read-only audit did not run tests. “Source verified” means the path is visible in code but lacks a matching end-to-end test. “Unverified” means no direct journey coverage was found.

## Entry routes and answer outcomes

| User journey | Trigger → visible result | Target context / execution | Evidence and status |
|---|---|---|---|
| Parent asks child, child asks parent, or delegated subagent asks owner | `ask_parent` / `ask_subagent` invokes the coordination backend with a stable inquiry identity. Target queues the request and reports queued/running/terminal outcome to asker. | Target runs a tool-free `InfoRequest` Sideband over a frozen context snapshot. Success carries the actual completed Sideband result reference and becomes an `InquiryAnswered` source owned by that target. Failure, reject, timeout, or cancel has no success proof and adds no consultation context. | Queue-before-work and target proof are source verified in [coordination.rs](../../../../crates/codegen/shell/src/session/actor/coordination.rs) and [answer proof creation](../../../../crates/codegen/shell/src/session/actor/coordination.rs). Proof ledger, owner and fork checks exist in the [coordination actor tests](../../../../crates/codegen/shell/src/session/actor/coordination.rs). The newly added joined receiver-side inquiry→InfoRequest→foreground provider test covers this receiving pipeline; a complete frontend tool/authentication/cross-process journey is not separately executed for every route. |
| Session asks peer via `ask_session` | Source gets its answer as the tool/API result. Same `(source, inquiry_id, payload)` retry returns/reuses the recorded request; changing target or question with the same ID conflicts. | The source does not get a synthetic second input. The successful target may receive passive context at its next permitted request. | Identity and retry coverage in [runtime identity tests](../../../../crates/codegen/shell/src/coordination/runtime/tests/identity_tests.rs) and route implementation in [runtime.rs](../../../../crates/codegen/shell/src/coordination/runtime.rs). Source-side no-duplicate behavior is source verified; target foreground incorporation is not exercised through the whole route. |
| External coordination API asks a Session | `grow/coordination/ask` returns a terminal outcome; `get` and `cancel` address the same source/inquiry identity. | No input is synthesized into the external caller’s source Session. If the target has a successful answer proof, only target-side context delivery is eligible. | [API handler](../../../../crates/codegen/shell/src/extensions/coordination.rs) and [design contract](design.md). API handler itself has no test here that proceeds through the target’s next foreground provider request. |
| Duplicate/retry or conflicting inquiry | A repeated identical request reuses the live/durable outcome. An ID with different source payload is rejected as conflict; the target does not run it a second time. | Existing successful proof can still be reconciled to target context on retry. No second success notification is intended. | [runtime retry/conflict tests](../../../../crates/codegen/shell/src/coordination/runtime/tests/identity_tests.rs) and [target duplicate check](../../../../crates/codegen/shell/src/session/actor/coordination.rs). Exact UI text for retries is not verified here. |
| Answer succeeds but receipt synchronization fails | Asker can already see `Answered`; target’s context receipt may lag until retry, live sampling boundary, or cold writer recovery. | Canonical terminal proof survives as an obligation. Reconciliation derives an owner-bound receipt from the proof; failures before receipt admission do not authorize injection. | [terminal and best-effort reconcile](../../../../crates/codegen/shell/src/session/actor/coordination.rs), [proof-to-receipt reconciliation](../../../../crates/codegen/shell/src/session/actor/coordination.rs). Recovery/fault tests cover replay and fork behavior, but not the full user/API route. |
| Target restarts during an open inquiry | A later retry sees a terminal `Unavailable`/TargetRestarted result instead of silently rerunning the interrupted request. | No success proof exists, so no context receipt is produced. A completed success proof can be recovered/reconciled without another Sideband call. | [cold recovery](../../../../crates/codegen/shell/src/session/actor/coordination.rs) and [ledger recovery test](../../../../crates/codegen/shell/src/session/actor/coordination.rs); source/test verified, not run in this audit. |

## Target phase and timing matrix

| Target phase at arrival / boundary | Trigger → user-visible behavior | Context and execution outcome | Evidence and status |
|---|---|---|---|
| Idle, ordinary actor | Successful answer creates a passive pending receipt. It does not auto-start a model turn. When a user/authorized turn starts, the receipt can be consumed into that Turn’s next request. | No provider call until the ordinary turn is admitted. `InquiryAnswered` is explicitly excluded from idle autostart. | Direct idle no-wake + next active-turn exact-selection test in [notification_drain.rs](../../../../crates/codegen/shell/src/session/actor/notification_drain.rs). |
| Foreground provider stream is blocked | Answer arrives while request is in flight. The request is allowed to finish; the answer is absent from that already-built request and appears at the next safe sampling boundary in the same Turn. | No parent-message interrupt or sampler cancellation; one Turn, two provider requests. | Real blocked-provider `handle_prompt` journey in [message_delivery_tests.rs](../../../../crates/codegen/shell/src/session/actor/tests/message_delivery_tests.rs). The original case uses a synthetic receipt; a later joined case also runs actual inbound inquiry/InfoRequest/proof while this real foreground request is blocked. |
| Foreground tool is running / tool result boundary | Answer is passive while tool execution is underway. After a completed tool batch the loop drains notifications before the next provider sampling. | Expected next request can include it; the tool is not cancelled. Specific tool-in-flight answer arrival was not found in direct `InquiryAnswered` coverage. | Loop ordering is source verified in [turn/mod.rs](../../../../crates/codegen/shell/src/session/actor/turn/mod.rs). Tool-phase concurrency journey is **unverified**. |
| Foreground waits on child | A successful child answer is delivered to the asking actor as the tool result, and the target child gets its own passive receipt. If the waiting foreground is the target of a separate consultation, passive context must wait for a sampling boundary. | The inquiry’s Sideband is independent of the foreground tool loop, so it does not itself provide foreground permission or cancel the wait. Exact overlapping wait-child + inbound answer path is not tested. | Tool-free Sideband path at [coordination.rs](../../../../crates/codegen/shell/src/session/actor/coordination.rs); no dedicated wait-child passive test found. **Unverified concurrency coverage.** |
| Successful model response, candidate final-close | Candidate snapshot is selected under the control gate. If eligible receipts are in that candidate, their durable consumption can authorize a successor request in the same Turn. Later receipts are excluded from that frozen candidate and remain pending for a later safe boundary/Turn. | Exact IDs matter: a later receipt cannot retroactively justify the candidate; consuming the candidate is required before successor dispatch. | Implementation at [interjection.rs](../../../../crates/codegen/shell/src/session/actor/interjection.rs), successor path in [turn/mod.rs](../../../../crates/codegen/shell/src/session/actor/turn/mod.rs). Passive consumption failure is tested for final and successor paths in [message_delivery_tests.rs](../../../../crates/codegen/shell/src/session/actor/tests/message_delivery_tests.rs). |
| Already final-closed | Receipt remains pending. It does not reopen the completed Turn. | Next permitted Turn may consume it. | Direct test [passive_inquiry_after_final_close_stays_pending_and_preemption_gate_wins](../../../../crates/codegen/shell/src/session/actor/notification_drain.rs). |
| Goal paused / budget or provider admission closed | Passive answer alone does not wake a paused or exhausted Goal. At a later authorized matching Goal continuation, Goal-owned obligations require matching goal/revision. This consultation receipt is Session-owned and therefore is not itself Goal-only. | Reconcile admission is withheld while execution is closed; ordinary active consumption also exits when Goal provider admission is closed. After a later valid turn, Session-owned context may be eligible; budget/behavior changes between receipt and a sampling boundary need direct integration confirmation. | [reconciliation gate](../../../../crates/codegen/shell/src/session/actor/coordination.rs), [provider-admission gate](../../../../crates/codegen/shell/src/session/actor/notification_drain.rs), [owner rules](../../../../crates/codegen/shell/src/session/actor/notification_drain.rs). Paused/budget restoration journey is **not directly tested**. |
| Execution suspended/terminated or actor closed | The original writer does not materialize a new consultation receipt while execution is closed. Existing canonical proof remains in target history; on restoration/reopen, reconciliation can materialize it before a subsequent active request. | No provider dispatch is implied by a committed answer or a receipt. A failed active payload read/consume is fatal before the dependent provider call and leaves the obligation available for recovery. | Suspended cursor/reopen/fork ledger tests in [coordination.rs](../../../../crates/codegen/shell/src/session/actor/coordination.rs); missing payload blocks real `handle_prompt` before provider in [notification_drain.rs](../../../../crates/codegen/shell/src/session/actor/notification_drain.rs). Full suspend→restore→provider journey is **not end-to-end covered**. |

## Recovery, fork, deletion, and concurrent routes

| Journey | Trigger → visible behavior | Execution/context consequence | Evidence and status |
|---|---|---|---|
| Receipt event committed, persistence ACK lost | Caller may observe a write failure despite durable receipt. Retrying the same logical ID should reconcile/find the durable fact rather than duplicate provider work or context. A failure before commit leaves no durable fact to recover. | This distinction is in the state-machine report; practical persistence fault coverage for the full `ask_*` path is not established by the direct passive-turn tests. | `implementation-verification.md` records model results; current source’s retry/reconcile paths above are verified. End-to-end injected ACK-loss journey remains **unverified**. |
| Fork or restore from history | A fork sees historical answer/audit but is not the original answer owner; it must not create a locally executable receipt from inherited proof. The original owner can reconcile after restoration. | No unauthorized cross-fork context injection. | [fork/reopen reconciliation test](../../../../crates/codegen/shell/src/session/actor/coordination.rs). |
| Delete the answering Session | An eligible delete request first passes existing storage/canonical preflight, then drains the live actor/writer and removes local history; rejection remains possible. Any target-owned proof/receipt in that history disappears with it. The asker’s durable outgoing result is separate and remains answerable from its own history. A new ask to the deleted target cannot resolve it as an online target. | No target receipt can later be restored from deleted target history; the source’s returned tool result is not re-injected. No dedicated delete-during-pending-consultation scenario was found. | [delete lifecycle](../../../../crates/codegen/shell/src/extensions/session_admin.rs), [history deletion](../../../../crates/codegen/shell/src/session/persistence.rs), API target routing [runtime.rs](../../../../crates/codegen/shell/src/coordination/runtime.rs). Outcome of deleting while the consultation is in flight is **unverified**. |
| Parallel asks to one target | Target serializes Sideband inquiries through a FIFO queue; each receives a separate stable identity/proof. When multiple successful answers are pending, a safe sampling drain can include all currently eligible receipts in received order, exactly once. Queue full after an active inquiry reports Busy/unavailable. | Foreground request is not interrupted by queueing/Sideband; answers wait as passive context. The implementation has a queue capacity of 32 queued inquiries. No direct test found for parallel successful asks followed by a single foreground request. | [queue and cap](../../../../crates/codegen/shell/src/session/actor/coordination.rs), [serial runner](../../../../crates/codegen/shell/src/session/actor/coordination.rs), [exact multiple-receipt passive test](../../../../crates/codegen/shell/src/session/actor/notification_drain.rs) uses synthetic receipts. Parallel end-to-end path **unverified**. |
| Parallel source send/retry, including two distinct inquiries with identical text | Same id and same payload deduplicates; same id with different payload conflicts. Different IDs remain separate obligations even if question/answer text matches. | Receipt identity comes from owner/source/inquiry identity and terminal version, not body text. They can each be consumed once; identical text is not a deduplication key. | [identity runtime tests](../../../../crates/codegen/shell/src/coordination/runtime/tests/identity_tests.rs) and [source/version derivation](../../../../crates/codegen/shell/src/session/actor/coordination.rs). Identical-text, distinct-ID foreground presentation is **not directly tested**. |
| Target approval, cancellation, rejection, timeout, or provider failure | Cross-workspace/undelegated requests wait for approval; rejection/cancel/timeout yields a terminal result. Cancellation during Sideband settles the attempt as cancelled. | These non-success terminals have no `InquiryAnswerContextProof`, therefore do not appear as context-only injection. | Approval and Sideband failure paths [coordination.rs](../../../../crates/codegen/shell/src/session/actor/coordination.rs) and [provider cancellation](../../../../crates/codegen/shell/src/session/actor/coordination.rs); source verified. No full terminal-to-no-injection user journey test was found in this audit. |

## Practical gaps to keep visible during implementation

1. The strongest new foreground tests inject a fabricated `InquiryAnswered` receipt. Separate proof-ledger tests exercise canonical success proof, recovery, and fork handling. The added joined test now connects actual inbound inquiry, Sideband proof, receipt reconciliation, real `handle_prompt` and the provider request. The separate frontend tool/authentication/API routes retain their existing regressions; this does not claim a full cross-process journey for every frontend.
2. No explicit real-actor journey was found for answer arrival during an executing tool or while foreground waits on a child, nor for Goal paused/budget denial followed by restoration. The source ordering/gates are visible, but this audit cannot claim the user experience for those concurrent cases is tested.
3. Deleting the target while an inquiry is queued/running and identical answer text from two distinct IDs have no dedicated integrated journey tests. The ownership/identity code supports the intended distinction; the user-visible behavior across those exact races remains unverified.

These are test-coverage statements, not claims that the paths are broken. The current docs do not establish behavior beyond the exact source/test evidence linked above.
