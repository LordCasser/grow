# Design

Use a single `sync_channel` of 64 complete records and a lazily started standard thread. `emit` and client ingestion call `try_send`; neither takes the writer mutex or waits on filesystem work. Each queued record is already bounded to 65,536 bytes, so pending payload stays under 4 MiB plus channel overhead. Pager batches are enqueued record by record rather than encoded into an unbounded combined buffer. A full/disconnected queue increments a process-local drop counter without invoking tracing from the producer. The next worker append writes a bounded diagnostic line with the coalesced drop count before the subsequent record. A worker that never resumes cannot report its own loss on disk; the queue remains bounded and producers remain responsive.

The worker is the only process-local caller of `LogWriter::append_lines`; existing cross-process inode locking and trim behavior stay intact. An append error is logged through tracing and does not crash the worker. The test redirect and snapshot request a barrier before changing/reading the writer path. A barrier waits at most two seconds to enter and complete the queue; timeout means the snapshot may omit queued entries. Normal `debug_log::flush` requests the same bounded barrier before flushing file-log guards. There is no attempt to kill a thread stuck inside the OS.

The regression holds the worker behind a test-controlled gate, saturates the queue, and checks that producer calls return without waiting for that gate and that the eventual file records the loss count. Existing writer/trim and snapshot tests protect format and append coordination.
