# 对抗性核对

| 替代解释或失败边界 | 核对结果 |
| --- | --- |
| 进程名称相同，是否归错了会话？ | 两次现场分别抓到完整父链，均归到 `grow --resume 01a19a05-5281-7201-bae3-89f599512353` 的 PID 3999；child summary 的 parent_session_id 和 canonical 工具输入一致。 |
| 是 Grow heap，而非外部进程吗？ | 原始 sample 明确标识测试 PID、cargo 父进程和二进制路径；Grow 独立 kernel peak 为 3.029 GiB。 |
| 只是很大的未提交虚拟地址吗？ | sample 字段是 footprint；`proc_pid_rusage` 也测得数十 GiB；超时退出后系统 Swap 从约 79.0 降至 7.14 GiB。没有用 VM Guard 总量作证。 |
| 是正常测试偶尔慢，延长时间就会结束吗？ | 环测试显式构造 n1/n2 闭环；关闭唯一长度上界后 cursor 不会变成 None，每轮追加 String。两次栈均停在该测试的 chain。延长时间只延长分配。 |
| 是否正式 Solaris 代码就丢失了环检测？ | 原工作区和正常备份均有长度上界；工具输入明确在隔离副本注入 if false。 |
| 是否只有临时副本污染，恢复后重跑即可？ | 第一轮确实污染第二轮；第三轮在显式恢复后又注入同一变异，因此恢复文件本身不足以约束下一次失控执行。 |
| 是否 Grow 超时没有收掉后代进程？ | 已观察到两次 timeout 结果及旧进程消失，第三次进程树也在 timeout 后消失。此次证据不支持孤儿存活；缺口是进程存活期间的资源预算。 |
| 能否把 timeout 算成测试成功杀死变异？ | 不能。它没有有限时间内断言失败的证据，还污染下一轮；脚本将所有非成功输出算 KILLED 的方式不足以分类资源中断和编译失败。 |
| 是否可以拿这次结论解释此前重启前的 50G？ | 不能。旧 PID 86472 的证据缺口仍在，本次归因只覆盖已采到的 PID 27031/32159。 |
| 调查是否干扰或重启了用户会话？ | 没有主动终止、暂停或重启进程，没有向另一个会话发消息；用户选择继续取证后仅采样和只读核对，退出由既有 Grow timeout 触发。 |

当前源码中的 Bash 支持单独配置 timeout 上界，不能以当前默认值或配置注释覆盖本次旧运行实例约 300 秒的实际结果。Atlas 查询没有返回相关 timeout 符号，时间结论使用 canonical 工具开始/结果事件，不依赖薄调用图。
