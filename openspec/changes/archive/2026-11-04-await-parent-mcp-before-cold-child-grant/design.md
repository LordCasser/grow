## Cause and ownership

The root starts MCP initialization in a background actor task. `apply_immediate_delegation_context` snapshots a live eligibility authority, but `freeze_child_mcp_grant` samples current client IDs before the background handshakes publish them. The frozen Bindings(empty) scope intentionally rejects later additions. Waiting for the root pool only after `load_session` cannot repair that admission.

## Implementation boundary

Add one internal initialized-pool snapshot request alongside the existing immediate snapshot. Its session activity waits through the existing MCP initialization state machine on a local task; the command executor remains available. The handle drops its reply receiver when the child-run cancellation token fires; the actor activity also ends when that receiver closes or the session's sideband cancellation epoch closes. Failed preparation returns the existing RestoreBlocked outcome with the original checkpoint, not a successful empty grant. The existing wait helper must not return immediately after it starts initialization. After initialization settles, the snapshot also takes the existing MCP publication-bridge mutex before reading the state, so the final catalog publication is complete. No new native deadline, connection retry, registry or persistent fact is introduced. Cold restoration selects the initialized snapshot; normal Spawn continues to sample immediately. A missing actor/reply fails child restoration rather than creating an empty authorized grant.

The snapshot remains a live authority. The established admission code still filters the original birth names and current profile/parent ceiling, freezes one current client-ID sample, and intersects actual calls with live authority. It never manufactures a missing birth fact, admits a newly configured server or reuses an old-process permit. Failed/unavailable parent handshakes settle under the existing startup policy and can legitimately remove a birth member.
