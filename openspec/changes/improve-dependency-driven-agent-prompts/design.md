## Context

本设计为无 Jev 的英文协作 prompt 改造。问题和范围见 [proposal.md](proposal.md)，实施前基线、逐处修改及保留边界见 [prompt-analysis.md](prompt-analysis.md)。方案已获用户授权进入专项实施，实际验证与剩余评估见 [verification.md](verification.md)。

核心选择是复用现有稳定 Audience、角色正文、task prompt 和任务工具。主 Agent 自己做任务拆分与语义依赖判断；运行时继续拥有任务生命周期、工具资格、通知、消息接纳和权限判定，不新增另一套调度状态。

## Goals / Non-Goals

**Goals:**

- 明确主从责任、最小充分依赖、工作就绪条件和验收证据。
- 在当前可用工具下减少不必要的整批等待、重复调查和错误前提造成的返工。
- 主 Agent 在自然检查点重新选择工作，subagent 在边界内自主执行。
- 交付可直接审阅的英文候选文本和能追溯到当前源码的修改说明。
- 通过装配回归和固定场景评估判断改造效果，不预设速度提升比例。

**Non-Goals:**

- 不引入 Jev、依赖检测模型、模型/effort 自动路由或 CPU 风格调度器。
- 不增加 DAG、任务数据库、artifact registry、文件锁、权限租约或父子消息类型。
- 不改变 wait-all、Sideband、通知时机、interrupt 的运行时语义。
- 不将普通任务变成 Goal 或 Workflow；不让 subagent 获取父会话生命周期所有权。
- 不把装配测试通过等同于模型行为和性能改善；真实评估完成前不归档 delta。

## Decisions

### 1. 保留现有装配层，不增设协作框架

| 信息 | 所有者 | 放置位置 |
| --- | --- | --- |
| 整体交付、分派和验收原则 | primary audience | 稳定 System head 中原有 primary 区段 |
| 局部自治、越界处理和返回原则 | subagent audience | 稳定 System head 中原有 child 区段 |
| 只读探索/端到端实现的方法差异 | 内置 Agent definition | 原有 Markdown role |
| 本次目标、具体依赖、修改范围、产物 | 委派方与当前任务上下文 | task prompt、结果与现有工作记录 |
| running/terminal、task ID、消息回执 | 现有 runtime | 原任务工具、Timeline 和通知 |
| 权限与单次调用批准 | 现有 Gate/permit | 不从文本约定推导授权 |

采用 audience 而不把主从协议写入 `standard.md`，因为 standard 同时用于主从 Extend role，且 Full role 可以省略它。采用局部 role 修改而不创建 planner/reviewer 新角色，因为当前问题是工作选择原则不够明确，不是缺少执行单元。

### 2. 使用产物依赖，规划到足以行动

委派应回答：需要什么结果、依赖什么已知输入、写入哪里、如何验证。依赖可以是已核对的调用关系、错误语义、某个接口定义或一个已验证的实现结果，不强制给每个事实创建版本对象或 task ID。

主 Agent 亲自核对影响全局的核心证据，同时允许已经能界定边界的独立探索开始。它不需要先了解所有细节再委派，也不能在不了解共享接口时派出多个相互依赖的写者。

每次任务启动或证据变化，只更新受影响的近期安排。远期步骤保留目的与未知，不反复重写整张计划。任务很小时直接形成最小闭环。

### 3. 就绪程度是消费条件，不是新的运行时状态机

| 判断 | 允许行为 | 不足以支持的行为 |
| --- | --- | --- |
| 可探索 | 读取相关代码、调查机制、准备问题与验收场景 | 不能把未知接口当作已确认事实 |
| 可实现 | 必要事实/接口和写入边界已经足够明确 | 不意味着集成正确或任务已验收 |
| 可验收采用 | 相应风险所需的验证已完成，前提仍适用 | 不自动代表所有下游和整个用户目标完成 |

这些概念放在自然语言的任务上下文中。运行时 `completed` 只表示已有执行终态，不替代语义验收；主 Agent 在现有工作记录里指出采用理由即可，不创建第二套 canonical lifecycle。

### 4. 主 Agent 按瓶颈选择工作，使用自然检查点

默认考虑顺序是：解除跨任务关键阻塞 → 验收能解锁后续的成果 → 自己负责的重要工作 → 当前范围内有价值的近期准备。它是选择原则，遇到更高价值的关键路径工作可调整，不实现硬编码评分器。

自然检查点包括一组相关读取结束、一个候选实现步骤结束、结果通知到达、关键事实变化或准备进入等待。没有新信号时不反复查询同一状态，也不为显得活跃定时重写计划。

可将多个独立任务后台启动。若 A 已返回、B 仍运行，而且 A 足以解锁 C，先核对 A 并推进 C；仅当下一项集成必须同时消费 A/B 时，等待两者形成实际依赖屏障。不能把工具的一次多 ID wait-all 说成按任意完成事件提前返回。

### 5. 第一版的中间成果通过阶段边界交付

当前子任务最终结果是可靠的交付入口。`ask_subagent` 可对已经在冻结上下文中的证据提问，但不能要求 Sideband 继续调查、验证新代码或修改前台任务。

因此，如果一个接口结论能提前解锁大量工作，可以将“确定该结论”划成独立且有价值的探索任务；任务返回并验收后，后续实现依据它启动。需要保留上下文时使用现有合法 resume 能力。不要把每个工具动作拆成阶段，也不要假设 child 有向父前台推送指导的工具。

有事实依据的 Sideband 回答可以作为判断输入，前提是明确它的快照范围；它本身不是 artifact acceptance、fresh verification、权限授予或全局计划提交。

### 6. 前提失效时收敛受影响工作

接口或共享假设改变后，主 Agent 标出受影响任务和产物，向仍运行的直接 child 发送已有干预消息。普通补充在下一步骤送达即可；继续沿旧前提执行将明显扩大返工时，可请求安全中断。

发送成功只说明 durable receipt。不能在收到回执后立即假定旧 writer 已停止并接管同一文件。仍需通过已有任务状态/结果确认安全交接；不可中断工具可能完成，完成后重新检查受影响产物。

本方案没有真正的“事务回滚”。共享目录的修改已经可见；只按实际归属处理自己的可恢复改动，不能自动丢弃他人工作。worktree 提供隔离，但接口语义仍需核对。

### 7. 子任务阻塞不转移父任务所有权

subagent 自行解决局部方法选择。缺少父级信息时可以 ask_parent 澄清；若需要父 Agent 实际调查、改变计划或执行操作，则返回已有成果和具体缺口。这样父 Agent 可以通过任务结果处理阻塞，不依赖 Sideband 启动其前台工作。

一个子任务部分受阻时，不受影响的部分可以先完成。不存在有价值的独立部分时及时返回，不能制造工作或一直等父会话。局部阻塞不会自行暂停父 Goal，也不会改变子 Agent 的工具资格。

### 8. 用成本与验收能力限制并发

并发收益必须覆盖启动、上下文传递、协调、验证和整合成本。简单任务可直接完成；有大量独立证据需要收集时才扩大探索覆盖。主 Agent 不能在已有多个待验收结果时继续无界派发。

模型选择遵循用户与运行时现有配置。项目级“确定性简单任务使用 luna xhigh”的偏好不固化为产品内置 audience，也不与 `TaskToolInput.model` 的使用约束混合。

child 的递归委派仍受工具资格、深度和现有简短说明约束。新协作正文不鼓励递归树扩张，也不为局部审查强制启动另一个 Agent。

### 9. 英文 prompt 单一候选，中文设计说明

[prompt-drafts.md](prompt-drafts.md) 是本 change 中候选模型文本的唯一完整副本。生产实施后以原有 `prompts/` 与工具说明为执行来源；这份文件保留为历史设计产物，不成为第二个加载源。

将 primary/subagent 文本限定在各自 `<audience>` 区段。保留 capability authority 和既有尾部工具速记。通用职责集中在 audience，role 只写方法差异，工具说明只写实际操作和必要任务信息。

### 10. 两层验证分别承担不同结论

确定性测试验证正确角色收到正确英文指引、Full/Extend 边界、权限文字保留、模板变量与工具说明一致。行为场景验证模型是否分派独立任务、及时采用部分结果、尊重写入范围、停止失效前提和避免无意义等待。

字符串出现不能证明行为改变；一次模型运行也不能证明普遍提速。执行记录、覆盖场景、成本和失败归因放在 change 内，按 [validation-plan.md](validation-plan.md) 决定是否接受候选文案。

## Risks / Trade-offs

- 固定 prompt 增长 → 记录完整渲染后的增量，优先删除角色重复文本；不因增加协调规则扩大每次回复的固定报告格式。
- 过度拆分 → 用“独立有用且可验证产物”约束粒度，简单任务评估必须覆盖。
- 指令被理解成“不能闲着” → 明确允许无独立有价值工作时等待，禁止重复劳动和范围扩张。
- 主 Agent 成为验收瓶颈 → subagent 完成局部验证，主 Agent 重点检查接口/前提/高风险和必要集成。
- 过早消费候选成果 → 区分事实、假设、候选、接受，并重新检查影响结论的输入变化。
- prompt 被当成并发锁或自动依赖检查 → 文档和规范明确它只规定协作指引，硬边界仍由已有 runtime 决定。
- 并行工作树变化 → 实施前重新核对 baseline 和重叠 change，不覆盖现有 capability 文本，不合并无关修复。

## Migration Plan

1. 保存方案、delta、英文草案和验证计划，区分设计、实施和模型评估证据。
2. 获得专项实施授权后，先与相邻任务确认写入边界，重新核对当前文件；只替换明确区段和 role 正文，保持 frontmatter 和协议。
3. 更新相关装配测试与开发者说明，执行有界回归，再执行场景评估；没有证据时不宣称性能提升。
4. 文案由正常编译发布到后续新建会话；已经记录的稳定 System head 不热替换、不重写历史。resume 是否获得新 head 以当时运行时真实构造为准，本 change 不新增强制迁移语义。
5. 若评估不满足要求，仅修订/恢复本次文案与对应测试，不回滚其他任务的工作树变更，也不重建 Timeline。
6. 所有场景和验证完成后才归档；执行全量与 archive 校验，将 delta 合入主规范。
