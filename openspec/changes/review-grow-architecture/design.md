## Context

审查基线是当前 `main`，不是历史 inventory 建立时的工作树。`openspec/specs/` 是已归档行为契约的唯一文档权威；源码、调用方、测试和运行结果用于证明当前实现是否满足该契约。历史 review、旧哈希和旧测试只作线索，不能替代当前证据。

## Decisions

1. **按行为切片而不是按 crate 宣称完成。** 一个特性可以跨 CLI、Shell、ChatState、sampler、leader、Pager 和存储层；审查沿真实入口追踪到最终状态所有者和客户端投影。
2. **主 Agent 保留跨模块综合。** 可并行委派互斥的只读证据切片，但缺陷定级、契约解释、反证和最终结论由主 Agent独立核对。
3. **先写不变量，再判断缺陷。** 每项 finding 必须说明触发条件、代码路径、违反的不变量、影响、修正任务和回归验证；无法证明的内容明确列为覆盖缺口。
4. **区分三类结果。** 阻塞契约验收的 actionable defect、非阻塞建议或验证缺口、与当前切片无关的既有债务分别记录，禁止借审查扩大实现范围。
5. **不在审查 change 中修业务代码。** 行为、接口、状态、安全或持久化修复必须另建 change，包含 proposal、delta spec、design、tasks 和验证记录。
6. **阶段性验证不等于总目标完成。** 每个特性阶段独立验证；提交和推送遵循用户明确授权。`tasks.md` 保留剩余切片，直到当前源码的全仓 review 和架构总图都有证据。

## Review Evidence Model

证据强度从低到高区分为：

- 静态机械证据：类型、分支、搜索结果、文件哈希；
- 局部行为证据：单元测试或 helper 测试；
- 跨模块/公开契约证据：真实入口测试；
- 持久化、安全、并发和数据完整性证据：故障注入、冷恢复、竞争控制与端到端验证。

较低层证据不能自动证明较高风险边界。未执行、超时、依赖锁或外部环境缺失必须原样记录。

## Risks / Trade-offs

- 仓库持续演进会使早期证据失效；每篇阶段报告固定基线提交，并在最终综合时重新检查漂移。
- 故障窗口和平台路径可能无法在当前环境动态注入；静态确认与动态覆盖缺口必须分开。
- 大型 Cargo 构建占用磁盘；按阶段检查 `target/` 和剩余空间，仅在本任务产物值得清理时执行 `cargo clean`，不删除其他任务可能拥有的构建产物。
